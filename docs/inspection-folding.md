# 已完成只读调用的历史折叠

开启压缩后，若旧正文省略和完整窗口保留仍不能满足 `max_context_bytes`，Sprig 才尝试折叠已完成的旧只读工具协议。它不调用模型生成摘要，不补读文件、不重放动作、不改变完整保存历史，也不提高请求上限。仍然放不下就停止发送。

候选仅为 `read_file`、`search`、`list_files`、`project_map` 的完整调用批次。所有调用和对应结果必须唯一、按顺序相邻且位于最近保护窗口之前。正文须已经在本轮请求准备中明确省略，或本来就是空的发现结果；后者保留完整的空数组、扫描限制和提示，不能变成“整个仓库没有匹配”的结论。

命令、写入、计划更新、错误、拒绝、未知/不可靠状态、仍保留的源码正文、读取标识和完整 SHA 都不折叠。一个混合批次只要有一个不符合条件，整批保留。重复 ID、未完成调用、结果错序或跨越保护窗口也不能折叠；不通过删除孤立消息来修补协议。

折叠只在连续合格区段内发生，不跨越用户消息、失败或其他保留批次。用一条明确标注 `context_folded=true` 的 assistant 历史数据消息替代该区段，按批次保存原助手文字以及 `[调用ID, 工具, 参数, 结果]` 行。第一条账本给出统一列名和历史提示，后续沿用。参数是 JSON 数据，不是新的可执行调用；结果保留状态、截断/完整性标志、计数和只读游标等剩余字段，仅去掉本轮已生成的重复省略提示。已经省略的正文仍标为 `context_elided=true`。

账本不表示当前文件状态、批准或验收通过。模型下一步仍须读取所需源码，后端继续检查版本、路径、只读、取消与新批准。原始调用 ID 仍在真实会话的已见集合中，模型重用它们会停止；应用不会从账本执行工具。完整会话中的原提案、结果和正文继续保存，恢复不会恢复旧读取标识的有效性。

`/context` 的 `folded_inspections` 列出区段和编码字节变化，`changes` 也标明 `fold_inspections` 操作。报告中的消息索引均指压缩前的原请求，折叠后的数组位置可能不同。用户消息和最近保护窗口保持原序、原值；失败与保留批次继续使用真实工具调用/结果结构。

每组最多 64 次调用，账本内部 JSON 在构造完整字符串前精确检查，最多 64 KiB 且不超过请求上限；超限区段拆分，单个过大的批次保持原样。参数和元数据解码也有限额，重复 JSON 字段不接受。解码后的结构再次脱敏，避免已配置凭据因原 JSON 转义而漏过字符串替换。每次替换至少节省 128 个实际请求编码字节，最终仍独立核对整个请求。

这不是经过验证的长期任务摘要。旧正文已经不可见，有限预算仍可能阻止请求；压缩只读历史协议不能证明模型会正确实现需求。相关窗口选择与取舍见[源码窗口](read-retention.md)。
