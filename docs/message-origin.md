# 用户请求与应用观察

协议中的 `user` 角色不总是用户的新任务。Sprig 也用该角色传递检查失败、后台结果、附件和运行提示，均是待分析的数据。现在由应用生成这些记录时保存内部来源标记；时间线、摘要和草稿重试依据标记区分真实输入，不根据正文前缀猜测。

## 当前行为

- `/timeline` 和分支选择只列真实用户消息。之后的应用观察保留在该轮中，直到下一条真实请求之前；原消息号保持，不重编号。附件快照或本地 `/verify` 观察本身不创建新的任务边界。
- 摘要投影保留最后一条真实用户要求的原话，不再让较新的检查失败或后台通知顶替它。摘要仍是有损模型报告，不保证全部历史语义已保留。
- TUI 恢复历史时以 `context>` 显示应用观察，真实输入继续为 `user>`。保存失败后，主输入框再次 Enter 根据真实用户要求判断重试，不把原任务重复加入历史。
- 固定检查、后台通知、输出限制、工作区变更说明、快照以及请求内的引用/摘要观察均保留其数据属性；来源标记不是新的任务、批准、文件读取版本或验收证据。

例如用户要求“保留错误消息中的引号”，随后应用检查失败：检查失败可继续反馈给模型，但不能成为新的用户轮次，也不能在摘要后代替原始要求。再次 Enter 仍遵守原预算和每个副作用的新批准。

## 保存与协议

内部标记为用户角色记录上的 `sprig_origin = "application"`。保存、加载和请求前验证类型；不得与输入递送身份、工具调用或原生推理状态混用。非法或脱敏冲突的保存记录不覆盖原文件，非法请求在 HTTP 前拒绝。

标记在协议投影前移除；不会作为未知 API 字段发送，也不改变现有正文。三协议的实际编码字节与同一正文去掉标记后的请求一致，不增加默认工具、上下文预算或模型调用。

**旧会话没有标记的用户角色记录保持原样。** 不凭“Application …”或其他措辞回填分类；因此旧应用通知仍可能显示为用户轮次。真正由用户输入或粘贴的同样文字也一直是用户输入。这是保守兼容规则，不是对历史来源的自动鉴定。

## 证据

源码修正前，两个回归分别复现摘要没有保留原任务、时间线多出检查通知轮次。另把 TUI 的选择器替换成旧的只按角色判断，真实 80×24 Enter 流程会在保存失败后重复加入原任务；当前选择器保持一次。检查失败状态仍是未验收，命令仍逐次批准。

新增 12 项回归覆盖上述路径、私有保存恢复、字面用户文字、附件、实际失败基线、后台/工作区/输出上限通知，以及三协议的非法来源拒绝和实际 HTTP 编码。最终本地范围见[机器记录](benchmarks/message-origin-20261024.json)。没有新增外部模型调用，也没有据此声称 Click 已修复或真实任务完成率提高；远程 CI 保持待验证。
