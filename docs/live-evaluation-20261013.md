首轮报告对应修改前的源码，后续报告分别保存执行时的驱动/输入/验收摘要，不用新的源码摘要改写历史结果。各报告保留原始总时长与扣除审批等待后的时长；加入间隔的报告另列 pacing 等待。不能把限流、审批等待、原始 wall-time 限制等环境因素误计为代码修复成功率，也不能比较未经对齐的时间作为速度排名。

mini 的两次运行均被操作员审查等待显著干扰，不能作为正常无人等待运行的性能成绩。第二次有一条批准提示因终端输出截断而无法完整审查，操作员拒绝了该动作；这是操作端限制，不能算作模型违规。后续对照需要先解决审批操作耗时与 SDK 壁钟预算的交互，同时保留逐次审批。

Sprig 有间隔的运行用时 386.014 秒，其中主动请求间隔等待 235.785 秒，HTTP 计时合计 147.593 秒；服务报告完整总 token 数 233,769。这些是返回的统计，不是实际账单证明。该次没有再遇到 429，却仍未开始修改，说明需要优先改进有限轮次内的任务推进和检索策略。一次运行不足以确定原因，更不能推断顶尖 agent 的整体水平。

本次新增 `--request-interval` 是评测选项，默认 0。两边使用相同间隔算法，明确记录等待，并维持不自动重试；mini 只扩展配置的间隔时间余量，仍有 SDK 壁钟约束与审批等待。产品 CLI 没有自动批准选项。完整参数与范围见 [固定仓库入口](repository-task-benchmark.md)。
