# Sprig 的其他产品方向：先把一个具体流程做顺

调研日期：2026-10-02。本文是设计提案，新增流程尚未实现。重点评估比“按需求撤回混合修改”更容易落地的方向。

## 判断方法

本轮查看官方文档、项目维护者仓库和作者论文，主动查找相似方案。没有安装运行所有竞品，也没有测量各方案的任务成功率。下文的实现难度是结合 Sprig 当前源码作出的工程判断，区别于竞品实测结论。

Sprig 已具备文件读取/搜索、Python 代码地图、精确编辑、带确认的命令执行、固定验收、会话保存和 Textual TUI。`run` 返回实际退出码、输出、超时与输出超限状态，但目前合并 stdout/stderr，不接受交互式 stdin，并在结束时执行进程清理；具体清理边界见[验证记录](validation.md)。这使有界的本地测试流程比较容易接入，长期服务器和任意终端交互比较难。Python 开发环境继续由 uv 管理。依据：[当前 README](../README.md)、[工具实现](../src/sprig_agent/tools.py)、[验收实现](../src/sprig_agent/agent.py)。

## 候选比较

| 方向 | 具体使用体验 | 收窄后的难度 | 差异化潜力 |
| --- | --- | --- | --- |
| 陌生仓库第一次跑通 | 打开项目后，找到入口、准备环境、实际执行一个最小验证，并留下可重跑入口 | 中低：先支持 uv Python 项目和有界命令 | 中等，取决于是否比对话里猜安装步骤省事 |
| 失败复现卡 | 从报错进入：复现 → 定位 → 修复 → 同一命令复验，最后带走本地问题报告 | 中等：先接现成测试失败，不自动最小化任意程序 | 中等，容易展示价值，也适合日常开发 |
| 陪练式编程 | 先给线索，用户自己改，Sprig 检查实际结果；随时切换为代写 | 中低：一题、逐层提示、工具权限模式 | 中等，需要明确服务学习者，教学效果要验证 |
| 轻量实验助手 | 将本地脚本的参数、运行版本、指标与输出文件关联，比较少量参数组合 | 中等：短时 Python 脚本和约定 JSON 指标 | 面向学生/科研脚本用户，定位较清晰；实验追踪本身不新 |
| 小补丁模式 | 给修改设文件范围与行数额度，在应用前展示是否越界 | 中等：先限制模型工具与候选补丁，不做撤回 | 面向担心顺手重构的维护者；预算和路径权限已有先例 |
| 项目工作流卡 | 常用操作有参数表单、步骤状态和重跑按钮，例如复现 bug、更新文档、准备提交 | 低到中：只提供顺序步骤与少量模板 | 单独较弱，适合作为其他流程的基础 |

“差异化潜力”是产品假设，不代表已有用户需求证据。以上概念都有先例；机会在具体用户群、默认流程和交互质量，不能声称全行业首创。

## 1. 陌生仓库第一次跑通

**用户例子：**“这个 GitHub 项目我刚下载，帮我在 Windows 上跑一个最小例子，告诉我以后怎么启动。”

TUI 显示三步：识别入口、准备环境、最小验证。README 的推荐命令和 Sprig 实际执行结果分别显示；每条命令带出处、当前目录和 argv。准备失败时，保留失败阶段，不把“安装成功”与“程序功能正常”混为一谈。成功后提供一个可以重新执行的本地入口卡。

**已有先例：**Aider 的 Ask 模式可讨论仓库而不修改代码；Goose recipes 已能保存工具、目标和提示供复用。[Aider 模式文档](https://aider.chat/docs/usage/modes.html)、[Goose recipes](https://goose-docs.ai/docs/guides/recipes/)。RepoProof-OS 的 README 描述了把环境、测试命令、项目地图与证据收据组织成仓库契约的设计，并标为研究 alpha；本轮未运行其发行包。这也是“仓库可运行说明”的直接先例。[RepoProof-OS](https://github.com/YucongDuan/RepoProof-OS)。

**Sprig 可做的区别：**把第一小时的摸索整理成简单的终端流程：用户知道停在哪一步，能修改候选命令，并直接复用已成功的步骤。无需开始就加入多 agent、容器编排或复杂知识库。

**最小版本：**

- 先识别 README、`pyproject.toml`、`uv.lock` 和 Python 入口；对不支持的生态给出说明，不猜成“已支持”。
- 有锁文件时提出 `uv sync --locked`，无锁文件时展示可能新增锁文件的影响；所有安装和执行仍取得现有操作确认，不静默改系统 Python。
- 用户选一个有界的 `--help`、小示例或测试作为验证；实际版本、命令与结果进入 JSON 卡片。Python 3.11+ 的 `tomllib` 与 `json` 足以处理首版数据。
- 不托管服务器、不安装系统服务、不自动迁移数据库；需要交互登录或长时间运行时标为当前不支持，并给可审查的步骤。

**验证价值：**在若干固定 uv Python 示例仓库中比较“普通对话”与“流程卡”的首次验证成功率、用户复制命令次数、阻塞原因可理解程度；不能用生成 README 字数衡量成功。

## 2. 失败复现卡

**用户例子：**“这条测试昨天还过，今天报错。先复现，再修，最后把复现步骤留给我。”

界面把一次失败保留为一个卡片：复现命令、文件状态摘要、Python/uv 版本、退出码、关键错误、已尝试的动作和最后复验结果。模型给出的根因先显示为假设；只有执行结果能更新“已复现”与“复验通过”。结束后导出本地 Markdown 报告，用户可以自己用于 issue 或交接。

**已有先例：**Aider 已支持 `/test`、自定义测试命令和编辑后自动测试修复。[Aider lint/test](https://aider.chat/docs/usage/lint-test.html)。Cline 官方提供 GitHub issue 根因分析 CLI 示例。[Cline RCA 示例](https://docs.cline.bot/cli/samples/github-issue-rca)。AEGIS 作者论文已经研究从 issue 描述生成 bug 复现；复现本身不是新概念，论文方法也不等于 Sprig 已具备同等能力。[AEGIS 论文](https://arxiv.org/abs/2411.18015)。

**Sprig 可做的区别：**围绕已有失败做一个轻量、可反复使用的本地入口，避免用户从很长的聊天记录里捞测试命令。先面向单人开发和交接，不建设远程 issue 平台。

**最小版本：**

- 用户提供失败命令；支持 pytest/unittest 的常见输出定位，以及普通退出码失败。无法解析时保留原始有界输出，标为未知错误类型。
- 在修复前执行一次，在修复后执行同一用户固定命令。失败后成功只是该检查的结果，不自动证明完整根因或所有功能正确。
- 记录版本、cwd、argv、退出码与超时/截断；首版不保存整个环境变量或自动打包全仓库。当前合并 stdout/stderr 的事实要写入报告。
- 复制“再次复现”先展示命令并沿用确认流程；导出的内容先允许用户查看，不自动发 issue、上传日志或附带凭据。
- 暂不做通用输入最小化、随机故障确定性重放、容器重建或自动 bisect。这些会显著增加复杂度。

**验证价值：**固定测试夹具里，卡片必须区分未执行、失败、超时、输出超限、已通过；修改测试以绕开失败应清楚显示。重新打开卡片能执行相同 argv；丢失的依赖和不可复现状态应明确报告。

Sprig 已在 chat 和 TUI 提供 [失败复现卡](manual-verification.md#失败复现卡)。卡片使用固定检查的退出状态、合并输出摘录和可配置文件采样；后续可以批准重跑同一命令或生成本地 Markdown 报告。它会列出内容变化的受跟踪文件，修改动机和完整根因仍需通过实际结果判断。

## 3. 陪练式编程

**用户例子：**“我想自己修这个解析错误。先给我一个线索，别直接贴完整答案；我改完你再检查。”

用户可以选“自己写”“一起写”“交给 Sprig”。自己写模式先定位相关源码，再按用户点击给出逐层提示。用户在外部编辑器修改后点击检查，Sprig 运行固定测试并解释观察到的结果。遇到困难可以切到一起写或代写；模式切换在 TUI 明示。

**已有先例：**Aider Ask 模式已经提供讨论而不编辑的边界。MIT 项目 agent-tutor 提供基于用户资料的学习计划、笔记和测验，也为 Pi 提供交互扩展。[Aider 模式](https://aider.chat/docs/usage/modes.html)、[agent-tutor](https://github.com/Mohamed-El-Sharqawy/agent-tutor)。另有更直接的 [Learning-first Coding Agent](https://github.com/starsstreaming/Leaning-first-agent-coding)：其 README 描述了提示、解释检查、留空挑战及禁止 agent 代写挑战文件的流程。本轮仅查看资料，未验证其教学效果；项目内陪练也不能声称首创。

**Sprig 可做的区别：**围绕用户正在开发的真实项目，用户动手修改，Sprig 在终端给线索和实际检查反馈。需要“自己解决的参与体验”，而不只是把回复换成老师语气。

**最小版本：**

- 首版每次只处理一个小目标；采用三级提示：定位、关键思路、完整示例。用户选择是否展开下一层，不猜测掌握程度。
- 工具层落实模式：自己写模式不向模型提供源码编辑和任意命令执行工具；用户可主动启动应用侧的固定检查。检查脚本自身可能写文件，必须展示实际检查定义，不能将此模式说成操作系统级只读隔离。提示词不能替代工具限制。
- 用固定检查验证代码表现，并区分“测试通过”和“理解正确”。不根据一次通过给用户能力打分，也不声称改善学习效果。
- 保存题目、已展开提示与用户选择即可；暂不建设课程体系、长期学情画像和复杂间隔复习调度。

**验证价值：**自己写模式的模型不能通过编辑工具或通用命令代写；提示展开次数可控；用户改变模式后有明确信息；用户修改过源码后检查的是新内容。真正的学习价值需要用户试用或小规模观察，而不是仅靠单元测试。

## 4. 轻量实验助手

**用户例子：**“这个统计脚本分别用窗口 7 和 14 跑一下，比较结果，记住每次用了什么数据和参数。”

TUI 展示少量运行的对照表：输入、参数、代码状态、环境、耗时、退出码、指标和输出路径。用户点开一行即可看到实际命令，再次运行前检查输入和代码是否变化。模型解释差异时引用具体运行；没有指标文件的运行只显示执行结果。

**已有先例：**[MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/) 已记录参数、代码版本、指标和产物；[DVC Experiments](https://doc.dvc.org/user-guide/experiment-management) 已保存和比较实验、参数及指标。[AI Scientist](https://github.com/SakanaAI/AI-Scientist) 也有 agent 执行实验的研究实现，其 v1 README 的模板面向 Linux/CUDA。记录实验和 agent 跑实验都不是独创，前两项也不是通用 coding agent。

**Sprig 可做的区别：**服务小型本地脚本，用户通过自然语言说明要跑什么，Sprig 协助准备脚本和执行，再直接查看参数与结果。是否比现有实验工具更方便，需要试用验证；不要求用户首版就配置完整实验平台。

**最小版本：**

- 只支持有界的本地 Python 脚本，一次最多少量串行参数组合；提供约定的 JSON 指标输出，暂不理解任意训练日志。
- 用 uv 管理环境，记录锁文件摘要、Python 版本、真实 argv、用户声明的输入文件摘要和输出位置。没有锁文件或未记录的外部输入要注明。
- 参数由用户指定或审查；随机种子仅在脚本实际支持并采用时记录为已设置。相同参数和锁文件不能保证所有运行数值相同。
- 首版使用本地 JSON 与 TUI 表格，不自建 MLflow/DVC 替代品；不做远程 GPU 调度、长时训练、自动调参或论文生成。

**验证价值：**两组参数的产物不会互相覆盖；表格能找到对应的真实指标文件；失败、取消、缺少指标和超时有独立状态；重跑能够说明版本或输入的变化。脚本执行成功与科学结论成立分别判断。

## 5. 小补丁模式

**用户例子：**“只修这个边界错误，最多改两个文件、增删不超过 60 行；锁文件和公共接口保留。”

TUI 在应用前显示候选补丁的文件清单、增删总行数、受保护路径及额度。超出明确范围时保留提案，让用户调整范围或采用更小的方案，不自动启动大重构。

**已有先例：**[OpenCode 权限](https://opencode.ai/docs/permissions/) 支持对工具和路径设置规则；[RepoProof-OS](https://github.com/YucongDuan/RepoProof-OS) 的 README 描述了 changed-files/line budgets 等验证。这些是范围控制的先例，不能据本次搜索宣布行数额度是新概念。

**最小版本：**

- 先实现路径范围、候选补丁涉及文件数和“新增行数 + 删除行数”的额度。明确相对本次任务基线计算，不把用户已有修改当成 agent 的额度使用。
- 候选补丁经程序检查，再用现有精确编辑及 diff 确认应用；文件内容变化则重新审查，不覆盖用户后续编辑。
- 严格补丁生成阶段不向模型开放通用 `run`，否则模型能通过命令绕过编辑工具的范围控制。应用侧固定检查仍有独立定义和批准语义；预算不能宣称限制任意命令的全部写入。
- 公共接口是否保持不能只由行数判断；首版把这项列为审查与相关测试要求，不承诺通用语义证明。不做需求级撤回或多文件原子事务。

**验证价值：**越界路径和超额候选在应用前拦截；已有人工改动不计入预算，也不被覆盖；“少改行数”和“行为正确”有分别的结果。行数少并不自动等于更好的修复。

## 6. 项目工作流卡

**用户例子：**“以后我只要选‘修失败测试’，填测试路径，Sprig 就按我们的固定步骤处理。”

把常用步骤显示为卡片和少量表单字段，例如检查 → 复现 → 提出修改 → 复验。每一步都能查看输入和结果，失败就停在具体步骤。项目维护者可以保存自己的检查命令和验收说明。

**已有先例：**Goose recipes 已提供参数、工具设置和可复用工作流，其 subrecipes 还支持分解任务；Cline 也提供 Skills 和自定义流程入口。[Goose recipes](https://goose-docs.ai/docs/guides/recipes/)、[Recipe 参数文档](https://goose-docs.ai/docs/tutorials/recipes-tutorial/)、[Cline Skills](https://docs.cline.bot/customization/skills)。因此“支持模板/Skills”单独不足以成为核心卖点。

**最小版本：**

- 内置两三个面向具体任务的卡片；本地 JSON 描述名称、文本参数、顺序步骤和固定 argv。
- 参数作为独立 argv 元素传递，避免拼接 shell 字符串；加载项目提供的卡片时展示命令，不能凭项目文件绕过现有确认。
- 不支持任意脚本语言、分支 DAG、并行工作流、第三方市场或后台调度。

**建议定位：**它是“第一次跑通”和“失败复现卡”的共用组件，可以顺手构建；不宜为追求创新而单独扩张成工作流平台。

## 本轮查到先例较多的方向

| 方向 | 已确认的直接先例 | 对 Sprig 的建议 |
| --- | --- | --- |
| 查看/管理上下文 | [DSH TUI](https://github.com/ArcaneOrion/dsh-tui) 有 `/context` 与消息队列；[LLM Context](https://github.com/cyberchitta/llm-context.py) 有文件选择预览、规则与上下文打包 | 做成实用辅助；不以一个上下文面板作为核心创新。显示请求前材料还需准确区分完整 payload、会话消息和源文件引用 |
| 卡住检测与人工引导 | [OpenHands StuckDetector 源码](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py) 检查重复动作/结果等；[Cline 桌面变更记录](https://github.com/cline/cline/blob/main/apps/examples/desktop-app/CHANGELOG.md) 描述循环后让用户选择换方法或停止 | 可补齐运行可靠性；不能把重复阈值当成通用“没有进展”证明 |
| 跨 agent 接力包 | [agenthandoff](https://github.com/czri23333/agenthandoff) 已从本地会话生成 Markdown 接力包与 continuation brief，并明确各格式的验证程度 | 可先导出 Sprig 自己的本地摘要；适配所有第三方会话会带来持续维护成本，单独差异较弱 |

以上判断依据文档/源码，与安装和运行测评有别。本轮没有收集用户私有会话，也没有安装这些项目。所查 OpenHands 源码中 context-window-error 检测仍返回 `False` 并带 TODO，不能因为类注释列了五种模式就声称五种均已实现。

## 建议优先顺序

若只选一个小功能，优先做 **失败复现卡**：现有固定验收、工具结果和 TUI 可以直接复用，首版也不要求长期进程和跨文件撤回。它能从真实报错进入，容易做一个可评价的演示。

若要选一个产品方向，优先验证 **Windows Python 项目跑通 + 失败复现卡**：发现入口 → 实际运行 → 失败排障 → 修复复验 → 保留可重跑入口。面向经常下载开源项目或维护小脚本的用户，并明确首版只覆盖 uv Python 项目和短时命令。

**陪练式编程**和**轻量实验助手**分别面向学习者与科研/数据脚本用户，是另两种定位；建议择一验证，不同时建设课程平台和实验平台。**小补丁模式**适合有维护经验、重视改动范围的用户，也可作为前述排障流程的一个选项。

共同的第一步是做一张卡片和一条固定流程，先让用户反复使用。根据试用结果再增加模板、其他语言和更多环境支持。本轮没有修改运行时代码，也没有执行模型 API 请求。
