## 发生过的恢复与证据边界

前两次调用猜错了源码目录；一次读取工作区外验收脚本被拒绝。后续诊断命令使旧 `read_id` 失效，首次编辑被拒绝；重新读取后又因替换正文缺少行结束符被拒绝。模型最终提交有效编辑，第 11 次请求后阶段检查通过，第 12 次请求后独立最终验收通过。没有放宽路径边界、读取标识或换行规则，也没有通过人工引导提供解法。

修复后的异常文件与已固定的公开上游参考文件**字节完全一致**。参考源码没有进入本次模型输入，但这是公开历史问题，无法排除训练数据记忆；此样本不能证明模型发现了未知缺陷，不能外推多文件任务、长会话或稳定成功率。既有 Click 未完成记录保持，不以 Requests 的一次成功覆盖它们。

## 未完成的第一条 mini 参考

同一模型、初始任务、Requests uv 锁和 12 次请求 / 2048 输出 token / 131072 字节预算下，mini-SWE-agent 2.4.6 的[第一次原生 SDK 运行](benchmarks/requests-mini-pre-timeout-fix-20261028.json)在第 5 次调用停止，报告为 `client_error`。4 次 HTTP 返回完整响应，第 5 次没有 HTTP 状态或响应正文，耗时 60020.895 ms；没有修复提交或最终验收。只有前四次的 15052 token，完整用量未知。

源码复核发现入口虽然接受 `request_timeout=120`，OpenAI 客户端、HTTPX 客户端和 LiteLLM 模型参数却都使用 `Config.timeout=60`，即命令上限。旧报告如实记录了实际 60 秒，不能把它改写成 120 秒；旧记录没有异常类别，不能仅凭约 60 秒的耗时认定当时的确切故障。

此批修正三层转发，使用 `request_timeout`，未设置时才回退 `timeout`；命令上限保持独立，报告同时记录两个数值。受控 SDK 请求先复现“指定 83 秒、实际携带 17 秒”，真实延迟 HTTP 先复现“指定 0.1 秒仍接收 0.4 秒后的响应”，修正后均通过。另将 HTTPX 的超时与传输故障映射为固定 `timeout` / `connection_error`，记录未知用量，关闭部分响应，不导出异常正文或自动重试。

第一条 mini 结果不能用于胜负比较。两端还保留原生工具和提示：Sprig 是 SSE、保留原生推理及阶段检查；mini 是 JSON、Bash 工具和提交后验收。任务和名义资源预算相同也不代表请求内容、客户端期限机制或运行条件完全一致。

## 修正后的全新参考

随后在新的初始快照运行一次[修正后 mini 参考](benchmarks/requests-mini-post-timeout-fix-20261028.json)。报告确认 HTTP 上限 **120 秒**、命令上限 **60 秒**。5 次请求取得完整响应，第 6 次在 120038.629 ms 触发 HTTPX 超时，没有 HTTP 状态或响应正文；固定故障为 `timeout`，未自动重试。前五次报告 26565 token，失败请求和完整用量未知。

该次仍未提出编辑命令或提交修复，最终验收未运行，不能标记通过；验收器与实际驱动完整性有效。基线及四条候选内观察获批，一条枚举工作区外任务父目录的提案被拒绝，没有给模型传递更正说明或参考源码。原生 SDK 入口结束后清理一次性候选，没有保留最终源码快照，因此不能补做独立后置验收，也不宣称候选完整性已由最终摘要证明。

两次 mini 的 HTTP/SDK 设置及结果分别保留，修正后的实际驱动摘要由报告绑定；它不是在干净旧提交上的运行，不把旧源码提交号当作修改后的驱动身份。单请求 JSON 等待、SSE 的增量 IO 和不同总期限机制也有差异。这仍是未完成参考，不能拿两个网络失败样本作为 agent 能力胜负证据；本批不扩大预算或继续追加模型请求。

## 后续

[本批验证记录](benchmarks/requests-live-validation-20261028.json)绑定冻结的 245 个源码及配置文件、三个原生数值报告和当前驱动。冻结后本地完整回归均为 1620 项：Windows 1599 通过、21 项平台跳过；WSL 1597 通过、23 项跳过。原 mini 与 Requests 两套环境在两端各 30 项 SDK 回归无跳过通过；最终 Windows Requests 五项集成检查包含三协议 JSON/SSE 子用例，无跳过通过。四项新增测试包括真实 SDK 序列化选项、实际延迟 HTTP、八类网络异常及部分响应关闭；初始失败日志摘要保留，修正后没有再改变功能源码。
