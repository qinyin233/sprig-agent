# 性能目标、基线与验证进度

目标是使 Sprig 的实际编码能力、响应速度和资源消耗接近当前顶尖开源编程 agent。当前还没有同模型、同任务的竞品对照，不能宣布达到目标，也不能用单元测试数量、功能列表或一次模型 smoke 测试代替性能证据。

## 对标和完成条件

以有公开编码评测协议的 mini-SWE-agent、OpenHands 作为复杂任务参考，Aider、OpenCode、Pi 作为日常客户端参考；当前排名和同模型成绩仍需直接验证。正式比较固定 release / commit、模型、服务、输入、基线代码、预算和验收脚本。保留 Sprig 的原生 Windows / POSIX、TUI、中途引导、只读、隐私限制和逐次批准。批准等待时间单独记录，不能靠关闭保护获得更快结果。选择依据、固定环境和入口检查见 [客户端对照准备](client-comparison.md)。

需要分别验证：真实任务成功率和失败类型；模型请求数、首段输出和任务总延迟；服务提供的实际 token 用量（缺失就报告未知）；工具结果和请求的字节数；检索覆盖率、工具耗时、内存与启动开销。复杂度应包括定位代码、修复错误、跨文件改动、新功能、测试反馈、多语言和长会话，包含失败与超限场景。比较使用各项目的正常工作流程，不能强迫竞品采用 Sprig 的脚本工具顺序。

先建立测量和修复可复现的瓶颈，再进行固定样本的真实模型比较；最终需要足够覆盖上述范围的直接对照证据。离线脚本只能验证执行器、协议和开销，不能代表真实模型的决策质量，也不能等同 Aider 的 [polyglot 编码评测](https://aider.chat/docs/benchmarks.html)。

## 已确认差距与实施顺序

1. **文件后部读取和上下文体积：本批落实。** 原先只返回文件开头；新增按行读取和后续行号。OpenCode 的 [read 工具](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/read.ts)和 Pi 的 [read 工具](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/tools/read.ts)均提供 offset / limit。
2. **代码地图重复解析、跨语言声明与关键词筛选：已落实基础索引。** Python 使用 AST，JavaScript、TypeScript/TSX、Rust、Go、C/C++、Java 使用锁定的本地 Tree-sitter 语法包；按语言与内容摘要缓存到有界内存，每次仍读取和校验文件。新增按路径或声明名查询，在输出预算内优先保留精确匹配。Aider 的 [RepoMap](https://github.com/Aider-AI/aider/blob/main/aider/repomap.py)有缓存和多语言语法解析；Sprig 当前还没有依引用重要性选择地图内容的排序、完整语义索引或调用图。
3. **请求与诊断任务测量已接入；真实模型任务与竞品对照待实施。** 当前测试进程没有 API 凭证，尚未进行真实模型任务对比；已记录请求/响应体字节、请求耗时、流式首段文本和服务报告的 token 用量，缺失或矛盾字段保持未知。本批新增任务验收与耗时框架；真实运行、失败样本和竞品适配仍需补齐，只使用进程环境提供的凭证和一次性工作区，不读取历史密钥或降低产品权限。
4. **复杂任务工具与上下文：按任务失败证据改进。** 重点检查多文件编辑、测试反馈、检索范围、长历史和输出预算，避免只做界面或错误文案优化。

已有 [编码任务诊断入口](coding-benchmark.md)：八个 Python / JavaScript 小型任务、37 个独立行为检查，逐次批准的真实运行入口、数值报告及可供其他客户端使用的相同输入导出。离线校准仅证明验收会拒绝原始错误并接受参考实现；当前没有真实模型成绩、竞品运行适配或外部真实仓库任务，不能因此宣布达到目标。

## 可重复的离线检索基线

```powershell
uv run --locked python scripts/benchmark-tools.py --compare-ref e9e8a8d --repeat 11
```

脚本创建一次性 UTF-8 项目，每个场景实际执行一次搜索和一次文件读取；支持范围的版本按搜索得到的行号读取两行，旧版本使用其原有文件开头接口。基线源码从明确指定的本地 Git revision 提取到临时目录，两版使用同一 uv Python、输入和输出上限。记录源码字节 SHA-256、commit、工作区是否有改动、重复数、目标是否读取到、返回 JSON 字节数及实际调用耗时，不请求模型、不执行项目命令、不修改用户文件。

测试场景是小文件、目标在大文件开头和目标在大文件后部；它们只代表基础定位后的读取能力，不能代表任意仓库检索或模型编码成功率。两版都能发现目标行号；旧版在后部场景无法用文件工具取得目标正文。范围版本会完整扫描受限文件，局部读取耗时可能增加；减少的是返回上下文，不能把字节减少直接换算成 token、费用或整体速度。

原始测量见 [Windows 读取基线](benchmarks/read-pages-windows.json)。平台差异和运行噪声需要分别测量；这里不设置不稳定的时间阈值作为 CI 正确性断言。

## Python 代码地图的冷启动与重复开销

```powershell
uv run --locked python scripts/benchmark-tools.py --compare-ref f3cd10c --repeat 11
```

扩展后的脚本同时测量 103 个 Python 文件、10,003 个符号的完整代码地图。两版使用相同输入和 1,000,000 字节的输出预算，比较首次调用与重复调用，并在两版中以相同包装函数统计实际 `ast.parse` 次数。这个输入可以完整返回，不能靠截断索引获得更快结果。

原始测量见 [Windows 地图缓存基线](benchmarks/map-cache-windows.json)。首次调用两版均解析 103 次；随后 11 次完整地图调用，旧版重复解析 1,133 次，缓存版为 0，两版输出的摘要完全相同。缓存仍进行文件读取、隐私校验、内容摘要、结果解码和输出构建。

首次建立缓存增加了编码和维护开销，重复调用减少了 AST 解析；需要同时报告两者。缓存最多保存 128 项，摘要与编码后符号元数据合计最多 1 MiB，这不是整个 Python 进程的 RSS 上限。超大结果不进入缓存，最旧且最近未使用的条目优先移除。这里的收益只适用于索引未改变且命中缓存的文件，不代表任意规模、多语言或模型总延迟的提升。

## 跨语言声明的覆盖与开销

```powershell
uv run --locked python scripts/benchmark-tools.py --compare-ref 542e670 --repeat 11
```

脚本增加 80 个一次性源码文件，分别覆盖 JavaScript、TypeScript、TSX、Rust、Go、C、C++、Java，每类 10 个文件，合计 810 个已知声明。测量首次完整地图、重复地图、实际原生解析调用次数和完整声明文件数；旧版本仅列这些文件的路径，因此不能把两版耗时直接当成同能力下的加速对比。原始测量见 [Windows 跨语言地图基线](benchmarks/multilingual-map-windows.json)。

本次 Windows / Python 3.13 测量，新版完整返回全部 810 个声明，首次地图 41.632 ms，11 次重复地图的中位数为 17.987 ms；首次原生解析 80 次，重复调用为 0。旧版返回 0 个声明，列路径约 0.5 ms；新版增加的是读取、隐私检查和声明发现能力，结果体积也从 1,899 增至 50,699 字节。Python 场景的完整输出摘要保持一致，首次耗时 147.247 → 151.202 ms，重复中位数 49.444 → 50.604 ms；这些小幅开销差异需要多次和多平台测量，不能宣布 Python 加速。此报告在全量测试结束后单独运行，避免测试和构建并发干扰。

非 Python 解析单文件限时 1 秒，语法遍历最多 100,000 个节点、4,096 个声明；超时和超限标记不可用且不缓存，原生解析前后及遍历中检查取消。语法包随 uv 安装，不在地图读取过程中下载。索引只提取声明及行号，跳过函数体内的局部声明，不能解析调用关系或证明真实编码任务成功率；基线也不覆盖所有语言语法或大型真实仓库。后续仍需测量实际模型任务、地图选择质量和整体资源消耗。

## 相关声明查询与输出预算

```powershell
uv run --locked python scripts/benchmark-tools.py --compare-ref b0300bd --repeat 11
```

一个 Python 文件含 1,001 个声明，目标函数位于最后。默认 16,000 字节预算下，原有地图会把过大的整个声明列表替换为路径和不可用标记。新增 `project_map(query="resolve_customer_route")`，按路径和声明名做字面匹配，优先保留精确名称、前缀、子串匹配；只输出匹配项，不读取函数正文给模型。匹配与候选选择过程中检查取消，仍检查新文件、隐私规则与受限读取，不以旧缓存或输出先满为由跳过范围内后部文件。

原始测量见 [Windows 查询地图基线](benchmarks/focused-map-windows.json)。同一输入、同一解释器，冷调用后各重复 11 次：

| 方法 | 输出预算 | 目标声明出现 | 返回字节 | 返回声明数 | 重复中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 旧版默认完整地图 | 16,000 | 0/11 | 77 | 0 | 1.404 ms |
| 旧版增加预算后的完整地图 | 1,000,000 | 11/11 | 50,910 | 1,001 | 1.945 ms |
| 新版默认预算下的声明查询 | 16,000 | 11/11 | 169 | 1 | 1.291 ms |

查询结果相对能覆盖目标的完整地图少约 99.7% 字节，这是主动省略无关声明的检索结果，不能宣称两版完整地图内容相同，也不能直接换算为 token、费用或模型成功率提升。未查询的完整地图输出保持相同；小幅时间差仍需更多真实仓库与多平台测量。CI 检查九种支持语言的查询、后部精确匹配、隐私更新、取消与严格 UTF-8 输出预算，不设置运行时间阈值。

查询模式有界保留候选，不能保证返回所有匹配；`matched_files` 仅指已扫描范围内的匹配文件数，`symbols_filtered` 与 `symbols_truncated` 区分筛选和进一步的预算省略。存在解析不可用、遍历/读取/输出超限时明确报告不完整。当前仍无引用图、语义索引或自然语言任务相关性推断，不等同 Aider 的引用排序，也不构成整体性能追平证据。

## Python 索引的元数据上限

缓存总字节上限只能限制保留的数据，不能阻止构建结果时的内存放大。一个 32,698 字节的有效 Python 文件，含 20,000 字符的类名与 512 个方法，旧实现会先生成超过 10 MB 的限定名称，再因输出预算省略声明。新增单文件 4,096 个声明、100,000 个实际遍历节点、每个限定名称 1,024 UTF-8 字节的上限，匹配其他语言的声明限制。名称在拼接重复父级之前先检查字符数，再检查规范化 AST 名称的实际字节数；超限结果不缓存、不返回部分列表，完整和查询地图都报告不完整，按路径查询仍可发现该文件。

```powershell
uv run --locked python scripts/benchmark-tools.py --compare-ref e51079965f25f0993734ad00a0ab0c8ea2ae9d15 --repeat 11
```

[Windows 原始报告](benchmarks/python-index-bounds-windows.json)使用同一 Python、相同输入摘要与 1,000,000 字节输出预算，每次建立新索引，实际调用只读地图。`tracemalloc` 只覆盖地图调用，排除夹具创建、导入和最终报告编码；测量的是 Python 分配峰值，包含完整 AST，不能当作整个进程 RSS 或原生分配量。

| 场景 | 旧版 / 新版 Python 分配峰值中位数 | 旧版 / 新版调用耗时中位数 | 行为 |
| --- | ---: | ---: | --- |
| 超长类名展开 | 31,024,709 / 2,345,024 字节 | 94.276 / 16.201 ms | 两版均返回同样的不可用标记，避免先构建超大名称列表 |
| 4,097 个短函数 | 12,287,490 / 12,287,490 字节 | 149.546 / 98.128 ms | 旧版完整返回，新版因声明上限标记不可用 |
| 普通类与 128 个方法 | 556,213 / 556,213 字节 | 6.189 / 5.938 ms | 两版完整返回同样的 129 个声明 |

第一种输入的 Python 分配峰值减少约 92.4%；这是特定内存放大场景的修复，不能推广为正常仓库或模型任务的整体加速。追踪分配本身影响计时，普通类的小幅时间差不构成加速结论。既有 103 文件 Python 地图与 80 文件跨语言地图的完整输出摘要也保持相同。

声明上限会使部分合法的生成代码失去完整索引，届时需使用搜索、按行读取和路径发现，不能把没有返回声明解释为声明不存在。上限不避免 Python 的完整 AST 分配，也没有为 `ast.parse` 增加原生超时；输入读取上限与取消检查仍保留。单文件边界、Unicode 名称、超限后恢复、取消时丢弃缓存、全地图及查询的不可用标记均有回归覆盖，仍需真实复杂任务验证。

## 请求级测量与未知数据

Provider 为每次调用生成纯数值记录，保留最近 128 条与累计计数；CLI `/usage`、TUI“查看请求统计”和 `--metrics` 显式展示。默认协议保持原样，`--request-usage` 才向流式请求添加 `stream_options.include_usage`，实际请求字节预算包括这个字段。不支持的服务不会自动重试。

首段文本时间在非空内容或拒绝 delta 通过基本文本格式验证时采样，纯工具响应与非流式响应为未知；完整响应后续校验仍可失败。总耗时包含网络、解析及文本回调，排除序列化、工具和批准。实际任务成功与采用响应的情况需另行记录，不能从 Provider 的协议成功推断任务正确。

只累计服务报告的三项通用 token 字段；未知字段不填零，部分请求缺失时完整总量为 `null`，另列已知部分与未知请求数。重复相同终态用量不累加，矛盾、非法或数值超界为未知；HTTP 错误不回显或收集正文。离线测试包含真实本地 HTTP 流、断流、取消、协议错误、预算拦截和 TUI 本地检查；这些证明测量实现与失败边界，不代表真实服务计费、真实模型成功率或性能追平。
