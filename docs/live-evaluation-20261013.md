评测修复提交 `8ea1927` 新增工具命中/覆盖/重复输出的数值诊断；仓库 mini 使用 SDK 原生壁钟配置 0，审批等待不再触发额外任务超时，仍执行原生循环、逐次批准、轮次上限、请求体预算及操作超时。22 项 SDK 回归包括模拟长时间审批等待、轮次上限和取消。Windows 本地 441 项测试中 427 通过、14 平台跳过；WSL 425 通过、16 平台跳过；固定 Click 校准仍为 635/642 与 642/642，均 0 跳过。

后续两边使用相同的 40 轮、262,144 字节请求体、60 秒请求超时及 20 秒请求间隔。初始快照、任务和外部验收保持固定。扩大预算与调整评测本身不是 agent 能力提升，不能拿新旧预算直接比较成功率或速度。

[Sprig 诊断运行](benchmarks/live-click-sprig-20261013-05.json)完成 11 次成功响应，第 12 次调用失败，HTTP 状态未知。12 次工具调用中，没有相同参数/输出重复；两次有效搜索分别匹配 1、6 行，均完整扫描 18 个文件、无跳过，另一次因 `context` 范围错误被拒绝；三个按行读取结果标记还有后续正文。这些证据不支持把此次停顿归为重复的无效检索。当前 60 秒配置下，一条成功请求的 HTTP 总计时为 30.472 秒；总计时包含连接与读取阶段，不能直接等同单次 socket 等待，仍不能认定旧 30 秒阈值导致截断或把历史错误全部归因为超时。

## 工具返回值检查与实现改进

[随机夹具结果探针](benchmarks/tool-result-consumption-20261013-01.json)用一次性本地文件生成三个独立随机标记，实际执行只读 `read_file` 后，分别通过工具 JSON、工具纯文本、用户数据对照发送结果。三个请求都准确返回各自标记，没有新增工具调用，服务报告合计 1,525 token。原始任务不包含标记；报告只保留布尔结果、数值计量和来源摘要，不保存标记、响应正文、密钥或会话。探针使用显式直连，只作用于该次探针，不改变产品网络默认值。

该检查的 assistant 读取意图由探针提供，只覆盖短上下文中的结果消费，不能代表自主选择工具、长会话或完整编码任务。结果不支持短上下文下普遍丢弃工具结果的假设，也不能排除更复杂场景的问题；没有因此更改工具消息角色。入口 `scripts/probe-tool-results.py` 必须显式传入 `--run`，只从进程环境读取凭据，不自动重试，已有报告会在读取密钥前被拒绝。两个本地 HTTP 回归覆盖真实请求链路和报告隐私，不调用模型服务。

实现提示现在明确要求按定位、必要的基线、修改、验证推进，避免把反复搜索一个尚不存在的符号当作实现；只读和审查任务仍返回发现。对任务必要的写入与命令，模型应提出具体可审阅的工具动作，由应用逐次请求批准。提示增加 791 个 UTF-8 字节；模型提出动作不会授予权限，代码中的批准、取消和路径限制保持执行。该提示尚未进行新的复杂任务真实复测，不能宣布任务成功率提升。

响应验证现在将 `tool_calls: null` 视作没有工具调用，允许已有的最终文字或拒绝文字正常返回；只有推理字段、没有最终文字或工具调用的响应仍被拒绝。推理正文不会进入返回消息或显示回调。这是兼容性修复，未记录 HTTP 状态且响应体为 0 的历史失败不能归因于这个字段。
