# 模型查看工作区图片

模型可用现有 `read_file` 的显式 `image=true` 模式查看工作区图片：

```json
{"path":"screenshots/result.png","image":true}
```

这条提案仍通过普通工具循环处理，必须先完整验证模型响应。支持与用户附件相同的 PNG/JPEG/WebP/单帧 GIF；普通 `read_file` 保持 UTF-8 文本行为，不自动把二进制转为图片。该模式不能与行范围、字节游标、声明或格式选项混用。

例如在 TUI 用 Enter 发送“运行项目现有截图命令，查看生成的图片，再调整布局”，模型可以分别提出命令和图片读取。每个命令照常批准；每次图片读取另有 `READ AND SEND IMAGE` 确认，显示路径、原始字节、尺寸、规范化摘要、模型和端点。以前的读取、模型要求或旧批准不会代替本次确认。需要支持视觉输入的模型，应用不自动切换模型、缩图或重试。

## 读取与确认

复用[图片附件](image-inputs.md)的无跟随文件句柄、隐私、完整解码和规范化：原始及规范化图片各至多 1 MiB，单边至多 4096、总像素至多 4 Mi，去除附带元数据，拒绝动画、损坏或编码冲突。源文件版本在准备前后及确认之后复查；模型动作沿用项目指令的已递送/审批复查。审批期间文件、隐私、指令、模型配置或资源状态变化会拒绝旧提案，取消也不保留像素。

像素不做 OCR 或凭据脱敏；因此每次显式确认的是把指定像素发送给当前模型，而不只是本地读文件。工具本身不发网络请求，后续请求仍须通过原有完整字节预算。

禁用 `read_file` 同时禁用图片模式，不增加另一个开关或模型工具。只读模式可在新确认后查看图片，仍不能执行命令或写文件。公开工具回执只含准备状态与元数据，不含 Base64 或编辑 read_id；超过 `max_output` 时明确省略元数据，确认内容不被静默截断。

## 像素生命周期

- 每次调用内至多保留 16 个规范化路径、合计 2 MiB 图片；同一路径重新获批读取会替换旧快照。新增超限时返回错误，旧快照保持，不静默逐出。
- 已批准的像素通过 Chat Completions/Messages/Responses 的原生图片块进入后续请求，包含真实 Base64 字节预算。工具结果 JSON 仍只是回执，`image_prepared` 不证明图片已实际发送或被模型正确理解。
- 新用户引导实际递送时清除这些模型读取的图片；之后需要重新提案和批准。当前调用结束、取消、错误或重置也清除。
- 启用私有会话保存时，图片读取只留下提案和回执，不额外保存本模式的原生像素块。正常模型回复、命令参数与已启用的原生状态仍按既有策略保存。恢复不会重读图片、重放旧批准或恢复缓存；历史准备回执不是本轮视觉证据，需重新读取。

这些规则与用户明确选择的 `--file`、`/add` 固定快照不同：后者仍可随私有历史保存，TUI `@` 仍是本轮用户选择。实时 `/ref` 不会因为模型图片读取而自动发送图片。没有新增任意 URL 图片获取、截图程序、图片生成/编辑或 PDF 后端；截图可由另外逐次批准的命令产生。

## 验证

15 项新回归含三协议 × JSON/SSE 六个真实回环流程，每条用获批命令生成 PNG、再获批发送像素、按实际像素修改文件、运行独立新批准的固定检查。另验证 80×24 TUI Enter、批准与拒绝、非布尔批准、审批中变更、只读/禁用/关闭资源、输出及缓存预算、规范路径替换、恢复不重放、新引导和请求超限前拦截。

这些是协议与执行链证据，没有外部模型调用，也不证明真实视觉理解或编码完成率提高。最终本地范围见[机器记录](benchmarks/model-image-reads-20261024.json)；远端 CI 按冻结要求待验证。
