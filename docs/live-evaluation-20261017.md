## 恢复与终端中断：总计40个响应

为判断硬预算是否是唯一障碍，恢复同一会话继续，未提供修复提示。恢复时旧读取标识失效，模型收到拒绝后重新读取并提出新修改，审批仍逐次进行。

第二次调用留下4个已保存的模型响应：添加公开异常、完成导出，另一个 core.py 提案停在审批前。随后原终端句柄丢失；系统进程检查确认对应进程已不存在，结束报告没有生成。核对文件证明待审批的 core.py 提案尚未写入，先保存中断时的私有会话和候选快照，再以剩余最多16轮恢复。没有在未知进程仍运行时启动第二份实例，也没有重放旧授权。

第三次调用中，应用为待定意图补上“未重放”结果。模型先读取当前文件，确认未应用后重新提案并取得新批准。历史前缀比较证明已保存的旧消息保持不变，没有插入操作者的后置验收结果或手工解题提示。[恢复数值报告](benchmarks/live-click-sprig-cli-ustc-deepseek-resumed-20261017-01.json)记录三次调用的已保存响应数为20、4、16，总计40。它不是一次新的20轮通过，也不是未经中断的一次40轮测试。

## 最终结果与可定位的问题

累计有6次文件写入、6次命令取得新批准；没有执行待定的旧提案。最终模型自选测试为729通过、1失败，失败是新测试把 CliRunner 包装的 `SystemExit(2)` 当作业务异常直接检查。它仍未以完成消息触发应用的固定验收，预算耗尽，CLI返回2。

操作者随后独立运行原外部检查：642项、640通过、2失败、零跳过，公开异常契约通过。剩余固定失败为 `test_unknown_options[--foo]` 和 `test_unknown_options[-f]`。候选测试的更新没有改变外部测试选择、断言或结果。因此本次任务仍未完成，不能把640/642或候选自测成绩当作通过。

另一处明确的接口错误是命令超时：运行时只允许60秒，模型看到的静态 schema 上限却为120秒，错误也没有说明实际数字；它依次提出120、120、100秒，均在审批前拒绝，浪费3个模型响应。后续修正让每个 Agent 的独立 schema 反映生效的命令上限，拒绝消息明确给出数字，并提示省略参数可使用该上限。HTTP超时不改变命令限制，不自动放大或截断用户请求。

本次真实记录验证编号读取、换行错误反馈和中断后重新检查/审批确实工作；没有证明它们提高多任务成功率，也没有同模型、同预算的竞争客户端新对照。超时修正另以实际回环HTTP及原生子进程回归验证，本阶段不再追加模型调用。
