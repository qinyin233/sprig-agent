# 长历史的请求准备内存

预算检查原先通过 `json.dumps(...).encode(...)` 构造完整请求再取长度。即使最终不发请求，超预算历史也已经分配了整份 JSON 字符串和 UTF-8 字节；压缩前后及旧工具字段还会重复做这些分配。

现在按 JSON 结构计数，字符串每次至多交给标准编码器 4096 个码点，精确累加紧凑 UTF-8 字节数。数字和字符串转义仍采用 Python 标准 JSON 编码器；最终请求也使用原编码器，不改变请求语义。预算预览和压缩计算完整长度，Provider 封包则在超过预算时提前停止计数，不构造完整超限请求，也不联网。发送前原有的实际字节长度检查继续保留。

计数边界会检查取消，完整保存历史、用户要求、失败与拒绝保留规则不变；不会自动丢弃失败输出、提高预算或重试模型。非法 Unicode 和不支持的请求对象仍在网络前拒绝，错误不回显原文。合法 JSON 的混合类型、对象键转换、控制字符和 Unicode 边界均与标准编码结果对照，另以真实本地 HTTP 回归检查发送字节。

## 离线测量

运行：`uv run --locked python benchmarks/context_memory.py --variant ascii`，可改为 `unicode` 或 `escaped`。每组 200 条消息，96 份较大的旧成功读取和三份小的最近读取，使用同一 64 KiB 请求预算。原始请求约 6.0–20.4 MiB，压缩后均为 40,426 字节。三组修正前后的输入请求摘要、压缩后请求摘要、字节数和省略条数均一致，原历史也保持不变。

Windows Python 3.13.0 的[数值记录](benchmarks/context-memory-20261017.json)：

| 数据 | 旧新增分配峰值 | 新新增分配峰值 | 旧中位耗时 | 新中位耗时 |
| --- | ---: | ---: | ---: | ---: |
| ASCII | 12,746,030 B | 317,226 B | 43.899 ms | 46.178 ms |
| 中文/emoji/组合字符 | 21,911,805 B | 393,672 B | 32.220 ms | 30.531 ms |
| 引号、反斜杠、控制字符 | 42,945,134 B | 325,407 B | 123.261 ms | 113.661 ms |

峰值指一次上下文准备中新产生、由 tracemalloc 跟踪的 Python 分配，不包括已创建的输入历史、解释器、整个进程 RSS 或模型服务内存。计时为同机串行运行的三次样本中位数，测量时未启用 tracemalloc；ASCII 样本略慢，不宣称所有场景全面提速。记录保存脚本和实际源码摘要；修正后在旧 HEAD 之上的工作区测量，`git_head` 仅是基线提交，不能当作修正代码的身份。

这证明该夹具上的请求准备内存改善和字节等价，不证明真实模型编码成功率提高，也不证明已追平其他 agent。真实任务预算、长时间进程内存和多客户端对照仍需各自验证。
